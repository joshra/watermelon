# Agent Guide

This project is a static single-player Suika-style watermelon game.

Read these files before doing any work:

1. `SPEC.md` - product, gameplay, asset, and acceptance requirements.
2. `progress.md` - current status, decisions, TODOs, and handoff notes.
3. `docs/ASSET_GENERATION.md` - AI asset-generation workflow and prompts.

## Current Priority

The user has explicitly requested this order:

1. Complete the specification and agent guidance first.
2. Generate AI assets with a consistent visual style.
3. Build the static game system after the above is clear.

Do not start gameplay implementation until the documentation and asset workflow are in place.

## Required Skills

Use these Codex skills when the task matches:

- `develop-web-game`: Use for game implementation, gameplay iteration, browser testing, screenshots, `window.render_game_to_text`, and `window.advanceTime(ms)`.
- `imagegen`: Use for AI-generated fruit sprites and any raster visual assets. Fruit assets must be generated by AI, not downloaded from icon sites or copied from the original Suika game.
- `playwright` or the browser tooling available in the environment: Use when validating the playable web page, controls, screenshots, and console errors.

If a future task involves editing a document, spreadsheet, or presentation, use the matching document-specific skill. This project currently does not require those skills.

## Non-Negotiable Requirements

- The game must remain a single-player static web page.
- No backend, database, account system, or online runtime dependency.
- Do not use CDN dependencies in the final game.
- The game must be a PWA: include a local manifest, service worker, install icons, and offline cache for the core static assets.
- Use exactly 11 fruit levels, in the order defined in `SPEC.md`.
- AI fruit assets must have one cohesive style across all fruit.
- Avoid original Suika game artwork or any third-party copied asset.
- Keep the first playable version focused: dropping, physics, merging, score, next fruit, game over, restart, desktop controls, mobile controls.

## Implementation Notes For Future Agents

- Prefer a single Canvas with a fixed logical game size of `480x720`, scaled responsively.
- Use Matter.js for collision and physics unless the user changes the requirement.
- Provide `window.render_game_to_text()` and `window.advanceTime(ms)` for deterministic automated testing.
- Keep PWA paths relative so the game can be served from the project root or a static subdirectory.
- Service worker caching must cover HTML, CSS, JS, local Matter.js, fruit PNGs, manifest, and PWA icons.
- The page registers `sw.js` with a version query and reloads once on service-worker controller changes so installed PWAs do not keep running stale cached `game.js`.
- Keep UI text short and avoid overlay clutter during gameplay.
- Current sound effects are synthesized with the browser Web Audio API in `game.js`; do not add external audio files or online audio dependencies unless the user explicitly asks.
- Test desktop/mobile viewport sizes and PWA registration before reporting the game as complete.
- After meaningful implementation work, update `progress.md` with completed items, test results, and remaining TODOs.

## Asset Handling

- Generated images may initially land under Codex's generated image directory.
- Copy selected final assets into this workspace under `assets/fruits/`; leave generated originals in place.
- If using chroma-key removal, keep only the final transparent PNGs as project assets unless intermediate files are useful for review.
- Do not reference assets from outside the project in `index.html`, `styles.css`, or `game.js`.
- PWA icons should be derived from accepted project AI artwork or generated with the same visual style; do not use downloaded icon packs.
